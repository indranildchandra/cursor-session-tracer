# /design-review — Adversarial Review Council → ADR

Run a multi-persona adversarial design review, then distil the outcome into an
**ADR** in `docs/adr/`. This is the *planning* half of the plan-vs-path model:
the ADR is the plan; a later cursor-session-tracer trace (linked by `adr_id`) is
the path; `audit_trace.py` checks the path stayed faithful to the plan.

**Personas live in** `.cursor/review-council/standard-personas/` (20+ files) and
`.cursor/review-council/user-generated-personas/`. **Load only the 3–6 you select** —
never all of them.

---

## Token budget — read this first

- In Phase 2 you select 3–6 personas. Read **only those files**.
- Each persona review runs in isolation — give it only its persona file + the
  domain profile + the scope brief. It must not see other personas' output.
- Keep each persona's returned assessment to ~300 words. If you're loading more
  than 6 persona files, reduce the council.

**Council size by complexity:** simple → 3 · medium → 4–5 · complex → 5–6.
**Always include at least one of:** `staff-engineer`, `cloud-cost-architect`,
`appsec-architect` (cost and security must always have a voice).

---

## Phase 0 — Scope + early human input

1. If this command was invoked with a scope argument, use it. Otherwise scan the
   repo for the highest-risk or most recently changed area and propose it.
2. Ask the human: *Is this the right scope? What worries you most? Any constraints
   (deadline, regulatory, perf/cost budget)? Any personas to add or drop?*
3. Record the answers verbatim as the **Phase 0 Human Brief**.

## Phase 1 — Domain fingerprint

Analyse the scoped code/design and produce (~200 words): tech stack, patterns,
top 2–3 risk areas, scale characteristics, and a **complexity rating**
(`simple` | `medium` | `complex`).

## Phase 2 — Persona selection

From the domain profile + Phase 0 brief, pick 3–6 personas from
`.cursor/review-council/standard-personas/`. Read only those files. Ensure at
least one of staff-engineer / cloud-cost-architect / appsec-architect. Show the
lineup to the human and confirm.

## Phase 3 — Independent review

Review the scope **once per persona, in isolation**. Each returns:

```
## <Persona Name>
**Stance:** proceed | caution | block
**Top findings:** - … - … - …
**Blocker (if any):** <description, or "none">
**Questions to council:** - … - …
```

## Phase 4 — Council debate

Put all Phase 3 outputs together. For each persona, write a 2–4 sentence response
to the challenges that touch its domain. Then extract:
- **Converged concerns** — flagged independently by ≥2 personas (highest signal)
- **Blocking concerns** — must resolve before proceeding (1 to raise, 2 to dismiss;
  the human may override any blocker, recorded with rationale)
- **Domain opinions** — valid tradeoffs that don't block
- **Open questions** — need human input

## Phase 5 — Human input

Present: converged concerns (≤3 bullets), any blockers, and 2–3 pointed questions
the council can't resolve alone. Wait for the human. Record answers verbatim. If
the human overrides a blocker, record: *"[Human] overrode blocker raised by
[Persona]: [blocker]. Rationale: [rationale]."*

## Phase 6 — Synthesis

State the verdict: `Proceed as-is` | `Proceed with modifications` (list them) |
`Redesign required` (list blockers). Produce action items with owners.

## Phase 7 — Record the transcript

Append the full session (composition, both rounds, converged/blocking concerns,
human input, synthesis, decision, action items) to `docs/design-review.md`,
**newest at the top**. Create the file with this header if absent:

```markdown
# Design Review Log
<!-- Append-only. Newest at TOP. Generated by /design-review. -->
```

## Phase 8 — Distil the ADR (the planning artifact)

The transcript is the argument; the **ADR is the decision**. Write it only when the
verdict is `Proceed as-is` or `Proceed with modifications` (a `Redesign required`
verdict loops back — there's no decision to record yet).

1. Next number = highest `ADR-NNNN` in `docs/adr/` + 1 (zero-padded to 4). Slug =
   kebab-case of the title.
2. Copy `docs/adr/TEMPLATE.md` → `docs/adr/ADR-<NNNN>-<slug>.md` and fill from the
   council output: **Context/Decision** (Phase 6), **Scope (files)** — the concrete
   files the decision touches (this is a **machine contract**: `audit_trace.py`
   parses it to flag drift, so be precise), **Alternatives**, **Consequences**
   (trade-offs + `Risks flagged by council` = converged concerns/blockers),
   **Council Verdict**, and a **Review record** pointer to the design-review entry.
3. Tell the human the new `adr_id` and instruct: *"When implementing, pass
   `adr_id=\"ADR-<NNNN>\"` to `start_trace` so the trace links to this plan; afterwards
   run `python audit_trace.py --session <date>/<id>` to check faithfulness."*

This closes the loop: **ADR = plan → trace = path → `audit_trace.py` = the check.**
